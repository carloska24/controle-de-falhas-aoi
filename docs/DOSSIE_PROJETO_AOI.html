Dossiê Técnico do Projeto - Controle de Falhas AOI

Documento consolidado por leitura do código para visão executiva e técnica do sistema: arquitetura, telas, fluxos, APIs, dados, riscos e plano inicial de melhorias.

Frontend: Next.js + React + TS Backend: Express + Prisma Auth: JWT em Cookie HttpOnly

1. Objetivo e escopo do sistema

Plataforma para controle de falhas de produção AOI, com operação por perfis (admin, operador, reparo, qualidade, almoxarifado e liderança SMT), contemplando registro de falhas, ciclo de OMs, requisições e relatórios analíticos.

2. Arquitetura e organização

Frontend

  • frontend/app/: rotas e páginas (App Router).
  • frontend/components/: UI e componentes de domínio.
  • frontend/lib/api.ts: wrapper de API autenticada.
  • Gráficos com Chart.js e notificações via toast.

Backend

  • backend/src/routes/: definição de endpoints.
  • backend/src/controllers/: regras de negócio.
  • backend/src/middleware/: autenticação e logger.
  • backend/prisma/schema.prisma: modelo de dados.

Dados

  • Entidades principais: users, registros, requisicoes, OMs.
  • Fluxo orientado por OM e status de registros/requisições.
  • Persistência via Prisma com provider PostgreSQL.

4. Fluxos principais do negócio

  • Operação: login → iniciar OM → lançar registros → pausar/retomar/finalizar.
  • Reparo: filtrar backlog → atualizar status de registro → exportar dados.
  • Almoxarifado: receber requisições → ajustar itens/quantidades → concluir entrega.
  • Qualidade: filtrar períodos/OM → analisar gráficos e indicadores industriais.
  • Administração: gestão de usuários e permissões por role.

6. Riscos e pontos críticos

  • Crítico: rotas de OM sem autenticação em backend/src/routes/omRoutes.js.
  • Crítico: /api/relatorio-falhas público em backend/server.js.
  • Alto: fallback fraco de segredo JWT no middleware de auth.
  • Alto: rotas de debug sem bloqueio explícito por admin.
  • Médio: divergências de documentação (README vs estrutura atual).
  • Médio: possível inconsistência de rota de redirecionamento para qualidade na home.

7. Recomendações iniciais para começar as melhorias

Fase P0 (segurança e estabilidade imediata)

  1. Proteger todas as rotas de OM com authenticateToken e revisar autorização por role.
  2. Fechar acesso público de /api/relatorio-falhas e demais endpoints sensíveis no server.js.
  3. Remover fallback inseguro de JWT_SECRET; falhar startup sem segredo válido.
  4. Restringir /api/debug/* para admin (isAdmin) e condicionar por ambiente.
  5. Padronizar logout e validação de sessão para reduzir inconsistência frontend/backend.

Fase P1 (qualidade de código e coerência funcional)

  1. Corrigir redirecionamentos por role na home para rotas existentes.
  2. Padronizar documentação raiz (pastas, comandos e versões reais).
  3. Consolidar rotas soltas do server.js em módulos de rotas para manutenção segura.
  4. Adicionar testes de integração para fluxos críticos: login, OM, registros e requisições.

Fase P2 (evolução arquitetural)

  1. Revisar modelagem Prisma para integridade referencial e governança de dados.
  2. Estruturar observabilidade mínima (logs padronizados + métricas básicas).
  3. Melhorar política de limites/rate-limit para rotas sensíveis além de login.
